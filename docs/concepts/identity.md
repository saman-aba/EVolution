# Identity Model

## 1. Purpose

Identity defines how EVolution distinguishes one logical object from another.

Almost every major concept in EVolution may require identity:

```text
Event
State
Measurement
Time Series
Pattern
Analysis
Context Entity
Decision
Source
Processing Graph
```

Identity is separate from:

```text
storage location
memory address
timestamp
version
representation
```

The fundamental question is:

> **What makes two representations refer to the same logical object?**

---

## 2. Logical Identity

Logical identity identifies an object independently of how it is stored or represented.

For example:

```text id="z5q4ra"
Event
    id = event-1842
```

may be represented as:

```text id="2ohj8s"
memory object
database record
serialized file record
network message
```

These are representations of the same logical event.

The physical representation does not define identity.

---

## 3. Identity vs Equality

Two objects may have equal values without being the same object.

For example:

```text id="5d3n5c"
Measurement A:
    metric = profit
    value = 10

Measurement B:
    metric = profit
    value = 10
```

Their contents may be identical.

They may nevertheless represent different observations.

Therefore:

```text id="b6p9a8"
equality
    ≠
identity
```

Identity determines whether two objects refer to the same logical object.

Equality determines whether their represented values are equivalent according to some comparison rule.

---

## 4. Identity vs Version

Version identifies a particular revision or generation of an object.

For example:

```text id="9q6x5e"
Analysis
    id = analysis-42
    version = 1

Analysis
    id = analysis-42
    version = 2
```

These may represent different versions of the same logical analytical object.

Therefore:

```text id="7a8g1v"
logical identity
    +
version
    =
specific representation
```

Not every object needs versioning.

Whether an object is versioned depends on its semantics.

---

## 5. Immutable Identity

Some objects should normally have stable identity throughout their lifetime.

Events are the clearest example:

```text id="2l9j51"
Event ID
    remains stable
```

If the interpretation or representation of an event changes, the system should not silently assign the identity of a completely different event.

Historical identity is particularly important for provenance.

---

## 6. Generated Identity

An identity may be generated by the system.

Conceptually:

```text id="p6c2sa"
create()
    ↓
generate ID
    ↓
object
```

The generation mechanism is an implementation detail.

Possible mechanisms include:

```text id="gqf5vl"
sequential ID
UUID
ULID
content-derived ID
domain-specific ID
```

No particular mechanism is required by the conceptual model.

---

## 7. Natural Identity

Some domain objects may have a naturally meaningful identity.

For example:

```text id="6x2i5s"
player = PlayerA
```

or:

```text id="j3kq89"
instrument = BTC/USDT
exchange = ExchangeA
```

Natural identity may be useful for domain entities.

However, a human-readable identifier does not necessarily provide sufficient identity semantics for every derived object.

---

## 8. Composite Identity

Identity may consist of multiple components.

For example:

```text id="nq8o7z"
Measurement
    metric = profit
    player = A
    session = 42
```

The combination may identify a particular logical measurement.

Conceptually:

```text id="9jv6p4"
Identity
{
    type
    components
}
```

The exact components depend on the object type.

---

## 9. Identity and Context

Context may participate in identity.

For example:

```text id="xv1j3z"
profit
    player = A
```

is not necessarily the same object as:

```text id="j5n0cm"
profit
    player = B
```

Likewise:

```text id="p8x5tq"
profit
    player = A
    session = 1
```

may differ from:

```text id="9crw3b"
profit
    player = A
    session = 2
```

Whether context forms part of identity must be explicitly defined for each object type.

---

## 10. Identity and Time

Time does not automatically define identity.

For example:

```text id="w0xq6m"
Event A
    timestamp = 12:00:00

Event B
    timestamp = 12:00:00
```

These may be two distinct events.

Therefore:

```text id="3h6j7v"
timestamp
    ≠
identity
```

This is why the Event Model separately defines event identity and timestamp.

---

## 11. Identity and Sequence

Sequence is also not identity.

For example:

```text id="5j6r8q"
sequence = 100
```

may indicate ordering within a stream.

It does not necessarily uniquely identify the event globally.

Sequence semantics depend on the stream and source.

Therefore:

```text id="c7v2dz"
sequence
    ≠
identity
```

unless a particular domain explicitly defines it that way.

---

## 12. Identity Scope

An identity may be globally unique or only unique within a scope.

For example:

```text id="0x6y5r"
global:
    event-123
```

versus:

```text id="6u2v4w"
session:
    action-123
```

where `action-123` may only be unique inside one session.

Conceptually:

```text id="g0r2g5"
Identity
    scope
    identifier
```

The scope must be known when interpreting the identifier.

---

## 13. Entity Identity

Entities are persistent conceptual objects that can be referenced by other objects.

For example:

```text id="e3c6h4"
Player
    id = player-42
```

Other objects can refer to that entity:

```text id="0p7r6k"
Event
    player = player-42
```

This avoids duplicating the complete entity description in every event.

Entity identity should remain stable while the entity remains the same logical entity.

---

## 14. Object Identity

Not every object is an entity.

For example:

```text id="m8q5wv"
Player
```

may be an entity.

But:

```text id="3q5k2s"
Measurement
```

may instead represent an observation produced from other information.

Both may have identity, but their lifecycle and identity semantics are different.

Therefore:

```text id="x6q2cf"
Entity identity
    ≠
Observation identity
```

---

## 15. Identity of Derived Objects

Derived objects should have identity when they need to be:

* referenced
* persisted
* compared
* cached
* traced through provenance
* invalidated
* updated
* exposed to other components

For example:

```text id="1n9h7f"
Pattern
    id = pattern-731
```

can then be referenced by an analysis:

```text id="3x8c2d"
Analysis
    evidence:
        pattern-731
```

---

## 16. Identity and Provenance

Identity allows provenance relationships to remain stable.

For example:

```text id="qj4j7b"
Event-100
   ↓
Measurement-500
   ↓
Pattern-12
   ↓
Analysis-9
```

Each object can reference another object by logical identity.

This allows provenance to remain meaningful even when the physical representation changes.

---

## 17. Identity and Storage

Logical identity must not depend on physical storage.

For example:

```text id="b8j2q5"
Measurement-500
```

may move from:

```text id="f1v4m6"
memory
```

to:

```text id="q3z7k1"
database
```

without becoming a different measurement.

Therefore:

```text id="6a4r9p"
logical identity
    ≠
storage address
```

---

## 18. Identity and Serialization

Serialization converts an object into another representation.

For example:

```text id="6d9w1a"
Measurement
    ↓
JSON
```

or:

```text id="9j3k6p"
Measurement
    ↓
binary representation
```

Serialization must preserve identity information when the receiving system needs to recognize the object.

The serialization format itself does not define identity.

---

## 19. Identity Collisions

Two distinct objects must not accidentally receive the same identity within the scope in which that identity is required to be unique.

Conceptually:

```text id="xq7m3p"
Object A
    id = 42

Object B
    id = 42
```

is invalid if both belong to the same identity scope.

The mechanism used to prevent collisions is an implementation concern.

---

## 20. Identity and Deduplication

Identity can be used to detect duplicate representations.

For example:

```text id="8q4s1f"
incoming Event-100
```

may already exist.

The system can determine:

```text id="6n3z8w"
same identity
    →
potential duplicate
```

However, equal content without equal identity does not necessarily mean duplication.

Two identical observations may legitimately represent two separate events.

---

## 21. Content Identity

Some objects may use content-derived identity.

Conceptually:

```text id="j4p9x1"
identity = hash(canonical_content)
```

This can be useful for immutable data.

However, content identity has important requirements:

* canonical representation
* stable serialization
* well-defined fields
* collision handling
* explicit version semantics

It should therefore be treated as an optional identity strategy rather than a universal rule.

---

## 22. Identity and Corrections

Corrections require careful identity semantics.

Consider:

```text id="q8w3s5"
Event-100
    original value
```

followed by:

```text id="r7y4n2"
Correction-200
    corrects Event-100
```

The correction is a new historical object.

It should not necessarily replace the identity of the original event.

This allows the system to preserve:

```text id="m6p2f8"
what was originally observed
```

and:

```text id="v8n3k5"
what correction was later applied
```

separately.

---

## 23. Identity and Versioned Algorithms

Algorithms themselves may have identity and version.

For example:

```text id="0r8m6j"
Pattern Detector
    id = trend-detector
    version = 3
```

A result can then reference:

```text id="n5x2v7"
algorithm = trend-detector
version = 3
```

This becomes part of provenance.

The algorithm identity is distinct from the identity of the pattern it produces.

---

## 24. Identity and Configuration

Configuration may also require identity when it is reused or referenced.

For example:

```text id="4h7q2p"
Configuration
    id = config-17
    version = 2
```

A processor can then reference the configuration rather than embedding an ambiguous collection of parameters.

This can improve:

* reproducibility
* provenance
* comparison
* configuration management

---

## 25. Identity and Lifetime

Identity does not necessarily imply indefinite lifetime.

An object may have a stable identity while it exists and later be deleted according to retention policy.

For example:

```text id="s3x8m2"
Cache Entry
    id = cache-42
```

may disappear after expiration.

The identity model should therefore remain independent from retention policy.

---

## 26. Identity Model

A generic conceptual representation is:

```text id="7g6j2k"
Identity
{
    type
    scope
    identifier
    version?
}
```

Not every object requires every field.

For example:

```text id="c3n8y7"
Event:
    identifier
    scope?

Algorithm:
    identifier
    version

Entity:
    identifier
    scope?

Derived Result:
    identifier
    version?
```

The exact identity structure is defined by the semantics of the object.

---

## 27. Identity Contract

Each major EVolution object should eventually document:

```text id="w8f3k2"
Does it have identity?
Is identity globally unique?
What is its scope?
Is identity immutable?
Is it versioned?
Can it be recreated?
Can two objects have identical values?
```

This prevents identity semantics from being accidentally determined by implementation.

---

## 28. Core Architectural Invariant

Identity is a semantic property of an object, not a property of its storage representation.

The core should provide mechanisms for:

```text id="e7t1q9"
identification
reference
versioning
comparison
deduplication
```

without imposing one universal identity strategy on every object.

Therefore:

> **Logical identity determines what object something refers to; representation, storage location, timestamp, and version describe how that object is represented or situated in time.**
